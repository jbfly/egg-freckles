The report (human, 2026-08-04, third hardware test):

    "Send to AI works, but when it sends the reply it comes back as Unfiled
    instead of the AI folder. And then it seems to file the ORIGINAL note that
    was sent into AI."


0. The wrong line
------------------

examples/harness-client/Main.newt, EF4, :FileReply:

    paperroll:NewNote(paperroll:MakeTextNote(body, nil), nil, nil);
    local entry := :FindNewest();          <-- the bug
    if (entry <> nil) and (tag <> nil) then
    begin
        entry.labels := tag;               <-- files whatever that returned
        EntryChangeXmit(entry, nil);
    end;

`:FindNewest()` is "the entry with the highest `_uniqueID` in the Notes union
soup". That is a *guess* at which entry was just written, and when the guess is
wrong this code files the wrong note. Both halves of the reported symptom follow
from one wrong answer: the entry it named got `labels := 'AI` (the user's source
note), and the entry it did not name stayed unfiled (the reply).

Nothing else in the client ever writes `labels`, so no other path can produce
the reported state.


1. Why the guess is unsound: `_uniqueID` is allocated per soup
---------------------------------------------------------------

Measured on this ROM. Two fresh soups on the SAME store, three entries:

    $ ns_eval '... st:CreateSoupXmit("effixA:probe", ix, nil) ... AddXmit ...'
    "A:0,1 B:0 nextA=2 nextB=1"

Each soup starts its own counter at 0 and keeps it. `soup:GetNextUid()` is
documented the same way — "the unique identifier to be assigned to the next
entry added to *the soup*" (refs/NewtonProgrammerRef20.txt:33348).

A union soup is a view over one member soup per store, so across a union soup
the IDs come from independent spaces and "the highest ID" is not "the newest
entry". EF4's own comment already knew this (Main.newt, :FindNewest: "a union
soup can interleave two stores whose ID spaces are independent") and its
mitigation — an `EntryModTime` tie-break — only fires when two IDs are *equal*,
which is not the failing case.

The physical MP2000 is a multi-store device: docs/installed-package-inventory.md
records 83 package payloads "across three stores" — Internal, a 4 MB Ultimate
Newton card and a 16 MB ATA card, the two cards alternating in the storage-card
slot beside the WaveLAN card. Whenever a card is in and the store the Notepad
adds to is not the store the tapped note lives on, the max-ID rule names an
entry from the other store; the most recently created note on the other store is
exactly the kind of entry it lands on.

NOT PROVEN, and stated as such: no `store_info` was captured during the third
hardware test, so which stores were mounted at that moment is unknown. What is
proven is that the rule is unsound on any multi-store device, that the device is
one, and that the fix does not depend on knowing which trigger fired.


2. Why the emulator round (l2build) passed, and why this one did too
---------------------------------------------------------------------

    $ ns_eval 'foreach st in GetStores() do ...'
    "Internal/-143364242 "

One store. With a single member soup the highest `_uniqueID` in the union soup
IS the entry just added, always, so the precondition EF4 relied on can never
fail here. EF4 was re-run on this instance under hardware-shaped conditions —
note typed into stock Notes through the UI, note open, envelope tapped — and
filed correctly every time:

    before send   "0:- 1:- 2:- 3:AI 4:- "        (4 = the source note)
    after send    "0:- 1:- 2:- 3:AI 4:- 5:AI "   (5 = the reply)

So this is not reproducible in Einstein as configured, and no emulator round
could have caught it. That is the finding, not an excuse: an identity was being
inferred where an identity was available.


3. The fix: hold the entry instead of searching for it
--------------------------------------------------------

Measured first, then written:

    $ ns_eval 'local note := pr:MakeTextNote("PROBE ONE", nil); local b :=
               IsSoupEntry(note); note.labels := tag; pr:NewNote(note, nil, nil);
               ...'
    "before=n after=y uid=3 lab=set"

`NewNote` turns the very frame `MakeTextNote` returned into the soup entry — it
is not a soup entry before the call and it is one after — and a `labels` slot
set on that frame *before* the add rides into the store with it:

    $ ns_eval '<dump every Notes entry as uid:folder>'
    "0:- 1:- 2:- 3:AI "

So :FileReply now files at creation and keeps the entry it made:

    local note := paperroll:MakeTextNote(body, nil);
    if tag <> nil then note.labels := tag;
    paperroll:NewNote(note, nil, nil);
    if (tag <> nil) and IsSoupEntry(note) then EntryChangeXmit(note, nil);

There is no search left on this path, so there is no wrong answer to file. The
source note is never written to at all.

:SaveNote had the same defect in a cosmetic form — it reported the id of
whatever :FindNewest() returned as "the note it just saved" — and now reads
`EntryUniqueID(note)` off the same in-hand entry.

:FindNewest itself is kept and unchanged for "Ask Note", where naming the newest
note IS the job and a wrong answer costs one wrong question, not a misfiled
note.

-----------------------------------------------

Fresh flash, EF5 the only package installed. `uid:folder` for every entry in the
Notes soup, before and after each send. `-` is unfiled.

    SECOND send, same note, same session (state carry-over test)
      after                        "0:- 1:- 2:- 3:- 4:AI 5:AI "
      source uid 3 still unfiled

    sketch note, 6 strokes drawn with the stock Sketches tool (uid 7)
      after                        "... 6:- 7:- 8:AI "
      real vision call: INK PROMPT ... , POST /ink 200
      reply text: "uid=8 lab=AI text=re: 6 strokesA simple outline of a house."

    mixed note, triangle + "what is this shape" (uid 9)

Every source note keeps the folder it had (unfiled); every reply, and only the
replies, carries 'AI. Screenshot effix-05-ai-folder.png is the AI folder tab
holding replies and nothing else.
