# mars "tntk broken builds" — re-diagnosis, 2026-08-08

## Bottom line
The prior handoff's theory (mars's **tntk binary** is corrupt and emits a
968-byte stub) is **disproven by direct test**. Both the mars binary and the
dev-box binary build the real app source into byte-size-identical, launchable
packages. The genuine root cause of the -48809 launch failure is tntk's
**zero-exit-on-source-error** behavior (partial `package0` stub written despite
`Uncaught exception:`), and that is **already guarded** by commit `8d933fd`
("Reject partial tntk package builds"), which is deployed on mars.

### Real source (examples/harness-client/Main.newt = 161997 bytes) -> 99096-byte pkg everywhere
| build | pkg size |
|-------|---------:|
| committed EF22 ref (f301fe73) | 99096 |
| dev box, dev tntk | 99096 |
| mars, dev tntk (after swap) | 99096 |
| mars, OLD tntk b88f4d17 (backup) | 99096 |

The last row is decisive: the "corrupt" mars binary builds the real app to the
same 99096-byte package. Header `package0xxxx` is normal even for the good 99KB
package -- it is not a stub signature. A minimal toy source builds to ~1KB with
a clean (no-exception) tntk run on both boxes; that is a valid tiny package,
not the failure.

### Actual -48809 root cause (repo evidence: mars-agent-pkg-download-20260807.txt)
tntk emits `Uncaught exception: kNErrUndefinedVariable` (e.g. undefined
`CellButton`) but exits 0 and writes a partial `package0` stub. It installs into
the store but launches with -48809 -> agent retry loop -> 300s codex timeout ->
"agent timed out."

### Fix already deployed
`newton_mcp.py` `tool_build_pkg`:
`if code != 0 or "Uncaught exception:" in output or not pkg.exists(): -> build failed`.
Commit 8d933fd, regression test `test_build_pkg_does_not_publish_tntk_exception`.
`git merge-base --is-ancestor 8d933fd a49a1b9` = YES (live on mars).
