EF6 — the tools long poll is package-wide now
=============================================

Instance `ef6round` (own container, seeded flash), `EggFrecklesEF6:jbfly`
v1.0-ef6, sha256 7cce547bbc1ff9955388427350ea632fc5ced1dc1865c6a2fdc2e1dfe2df38d9.
Host `runtime/raw_pkg_server.py` on 18081; log `runtime/logs/ef6round-pkg.log`.

The fifth hardware test's second finding: an agent-driven install to the MP2000
failed with "Newton not responding to pings" because the human had the Egg
Freckles *window* closed, and the poll only ran between Boot and ViewQuitScript.
EF6 gives the poll to the package-level install-hook agent — the same frame that
owns "Send to AI" — so InstallScript starts it at every boot and no view can
stop it.

3. A reconnect storm, found and fixed because of this move
----------------------------------------------------------

The first EF6 build answered every op but reconnected constantly. Measured
against the host's own log:

    reconnects in 60 s, first EF6 build:   15   (one every 4 s)

and every one of them was the Newton hanging up, not the host: instrumenting
`ToolBroker.serve` temporarily showed all five failures in 30 s were
`ConnectionError: persistent Newton connection closed mid-response`.

Cause: `:ToolConnected` started a **new** self-rescheduling `:ToolWatch` chain on
every connect, and old chains never died, so `toolMisses` was incremented once
per chain per 4 s. Three chains cross the "> 2 misses" threshold inside one
period, the channel tears itself down, reconnects, and adds a fourth chain.

This was always latent — it only became visible when EF6 made the poll run for
minutes instead of for as long as a window happened to be open, and it is very
probably the "stale-poll 504s after window-close cycles" the fifth hardware test
reported. Fix: a `toolWatching` flag so exactly one chain exists.

    reconnects in 60 s, shipped EF6:        0
    connects in the whole 12-minute session: 5

With one chain the host's 3 s heartbeat always resets the counter before the 4 s
tick, and the connection simply stays up.


4. The poll survives a big ink encode
-------------------------------------

A ping fired two seconds after a "Send to AI" on a 37-stroke, 2569-point note —
while the Newton was collecting, thinning and encoding a 5585-byte body —
answered `pong` in 5.77 s. Slower than idle, because the encode holds the
NewtonScript event loop, and well inside the timeout.
