0. How you reach the drawing tools in stock Notes
-----------------------------------------------------------------
There is NO "sketch" stationery.  The `+New` picker offers only
Note / Checklist / Outline / Recording
(runtime/evidence/sketchprobe-02-new-picker.png).

The drawing mode is the *recognition mode*, set from the `A` button in
the Notes bottom bar at screen (30, 425).  Its popup is
(runtime/evidence/sketchprobe-05-styles.png):

    A  Text          tap (88, 354)
    ~  Ink Text      tap (88, 369)
    #  Shapes        tap (88, 387)
    ~  Sketches      tap (88, 402)
    i  Preferences   tap (88, 422)

Choosing Sketches replaces the `A` glyph with a pen squiggle
(runtime/evidence/sketchprobe-06-sketches-mode.png).  A "sketch note"
is therefore an ordinary class 'paperroll note that happens to contain
drawn objects; it is not a distinct stationery.

3. What one drawn stroke looks like in `data`
-----------------------------------------------------------------
$ ... for i := 0 to Length(d)-1 ... ClassOf(o) ... foreach tag, v in o ...
"[0] class=frame slots=ink:ink2 viewBounds:frame _proto:frame |
 [1] class=frame slots=ink:ink2 viewBounds:frame _proto:frame |
 [2] class=frame slots=ink:ink2 viewBounds:frame _proto:frame | "

Three strokes drawn -> three separate data items.  No viewStationery
slot at all; the payload is a binary of class 'ink2.

$ local o := e.data[0]; "inkclass=" & ClassOf(o.ink) & " inklen=" &
  Length(o.ink) & " vb=" & ... & " protoslots=" ...
"inkclass=ink2 inklen=10 vb=58,82,63,186
 protoslots=viewClass:int viewFlags:int viewFormat:int
            points:polygonshape debug:int "

TRAP: the item's `_proto` is a clPolygonView template that carries its
own `points` binary, so `o.points` resolves through the proto chain even
on an ink item — and it is degenerate:

$ ... PointsToArray(o._proto.points) for i := 0..2 ...
"[0] pts=14 0 | [1] pts=14 0 | [2] pts=14 0 | "

shape type 14, zero points.  Reading `o.points` on a sketch stroke gives
you an empty polygon, not the geometry.  Test `o.viewStationery` first.

4. Cracking 'ink2 — ExpandInk works on the raw soup frame
-----------------------------------------------------------------
$ local o := e.data[0];
  PolyContainsInk(o) ... ExpandInk(o, 0) ...
"polyContainsInk= expand=strokeBundle slots=class:symbol bounds:frame strokes:Array "

PolyContainsInk returns nil (it wants a live clPolygonView), but
ExpandInk accepts the soup data frame as-is and returns a stroke bundle.

$ local b := ExpandInk(o, 0); local s := GetStroke(b, 0);
  local a := GetStrokePointsArray(s, 0); ...
"vb=58,82,63,186 bbounds=58,82,63,186 nstrokes=1 npoints=17 alen=34
 pts=84 60 94 60 103 60 111 60 117 60 122 60 126 60 130 60 134 60 138 60
      142 60 146 60 151 60 157 60 165 60 174 60 184 60 "

17 points, alternating Y,X (Point Arrays, refs/NewtonProgrammerRef20.txt
:27164-27171).  A vertical line at x=60 running y=84..184.

-----------------------------------------------------------------
5. Cross-check against the /drag inputs
-----------------------------------------------------------------
$ for i := 0 to 2 ... ExpandInk / GetStroke / GetStrokePointsArray ...
"[0] ns=1 np=17 first=(x60,y84)  last=(x60,y184)  vb=58,82,63,186 |
 [1] ns=1 np=89 first=(x100,y84) last=(x180,y185) vb=98,82,182,186 |
 [2] ns=1 np=17 first=(x210,y104) last=(x280,y104) vb=208,102,282,107 | "

  stroke | dragged (screen)          | stored (note-local)      | delta
  -------|---------------------------|--------------------------|--------
  A      | (60,120)  -> (60,220)     | (60,84)  -> (60,184)     | 0, -36
  B      | (100,120) -> (180,220)    | (100,84) -> (180,185)    | 0, -36
  C      | (210,140) -> (280,140)    | (210,104) -> (280,104)   | 0, -36

X is exact.  Y is off by a single constant, 36, for every stroke: the
coordinates are in the paper roll's own space, not screen space, and the
36 is where this note sits under the current scroll.  All strokes in one
note share one space, so a host renderer normalises against the note's
own bounding box and never needs to know it.

10. The inverse path also works (Track I3 write direction)
-----------------------------------------------------------------
$ MakeStrokeBundle([[10,10,20,20,30,30,40,40]], 0) -> CompressStrokes
"bundle=strokeBundle ns=1 np=4 compressed=frame slots=ink:inkWord viewBounds:frame "

CompressStrokes returns exactly the `{ink, viewBounds}` shape a note's
data array holds — but as 'inkWord (2.x ink text), not 'ink2 sketching
ink.  One documented conversion fixes that, and the geometry survives:

$ InkConvert(p.ink, 'ink2) then ExpandInk({ink: i2, viewBounds: p.viewBounds}, 0)
"orig=inkWord origlen=16 conv=ink2 relen=8 ns=1 np=17
 pts=10 10 13 13 16 16 18 18 20 20 21 21 23 23 24 24 25 25 26 26 27 27
      29 29 30 30 32 32 34 34 37 37 40 40 "

Host points in at (10,10)..(40,40), same points back out, interpolated
to 17.  A host-generated drawing can be written into a native note.

11. Ink Text mode adds NO data item — it embeds ink words in a 'para
-----------------------------------------------------------------
Two strokes drawn in Ink Text mode (sketchprobe-14-inktext.png):

$ ... classify every item again ...
"n=10 0=ink2 1=ink2 2=ink2 3=ink2 4=ink2 5=poly 6=poly 7=poly 8=poly 9=para "

Unchanged at 10.  The ink went INTO the existing paragraph:

$ local o := e.data[9]; foreach tag, v in o ...
"slots=viewStationery:symbol viewBounds:frame text:string _proto:frame
 styles:Array  isStr=1 textlen=30"

$ Length(o.styles), ClassOf of each, and Ord() of each character of o.text
"styles n=8 0=int 1=int 2=int 3=inkWord 4=int 5=int 6=int 7=inkWord
 codes=110 111 116 101 32 112 114 111 98 101 32 63233 32 63233 "

`text` is a plain string, "note probe " followed by placeholder character
63233 (0xF701) once per ink word.  `styles` is the usual alternating
[runLength, style] array, and the style for an ink run is a binary of
class 'inkWord.

That binary expands too — the same InkConvert bridge as section 10, with
GetInkWordInfo supplying the bounds:

$ local w := e.data[9].styles[3]; GetInkWordInfo(w); InkConvert(w, 'ink2);
  ExpandInk({ink: i2, viewBounds: {0,0,origWidth,origAscent+origDescent}}, 0)
"class=inkWord len=22 w=52 asc=7 desc=0 conv=ink2 ns=1 np=46"

So all three ink representations on this ROM are extractable:
  'ink2    (Sketches)  -> ExpandInk directly
  'poly    (Shapes)    -> PointsToArray
  'inkWord (Ink Text)  -> InkConvert(w,'ink2) -> ExpandInk, bounds from
                          GetInkWordInfo

Consequence for any text extractor: a paragraph containing ink words
yields character 63233 in its text.  A7's ReadNote would put that raw in
a prompt.

12. Which note is "newest" — timeStamp is creation time only
-----------------------------------------------------------------
$ walk the timeStamp cursor, printing id / timeStamp / EntryModTime /
  Length(data)
"id0 ts=64461125 mod=64461125 n=-1 | id1 ts=64462106 mod=64462106 n=-1 |
 id2 ts=64464021 mod=64464021 n=-1 | id3 ts=64477370 mod=64477379 n=10 | "

The sketch note's creation stamp and modification time are NINE minutes
apart: drawing updates EntryModTime and never touches timeStamp.  A
drawing added to an existing page therefore never becomes "newest" under
`Query({indexPath: 'timeStamp})`, which is what
examples/harness-client/Main.newt:677 orders by.

And you cannot index the other way:

$ GetUnionSoupAlways("Notes"):Query({indexPath: '_modTime}) ...
" modQuery=EX evt.ex.fr.store"

There is no modification-time index on the Notes soup on this ROM.
(The three n=-1 entries are the seed flash's data=nil failed writes,
docs/notes-bridge.md N2/N3.)

A modal "Sorry, a problem has occurred. (-48601)" appeared once during
drawing and swallowed the two strokes issued while it was up
(sketchprobe-08-cross.png).  Dismissing it and redrawing worked
(sketchprobe-10-cross.png).  The seed flash is documented as throwing

noise, not a sketch defect.  A client that reads notes should still
expect an alert can eat pen input on this ROM.

All /drag strokes are straight lines — the control API's drag is
start->end only (emulator/control.py:185).  The digitizer still sampled
17-89 points per stroke, so the capture mechanism is the same one a
freehand curve uses; only the shapes are simpler.
