5. Modification order — the cat/D&D bug, dead
-----------------------------------------------------------------
The hardware failure was: draw a cat, tap Ask Note, get an answer about an
older D&D *text* note, because timeStamp is creation time.

Set up deliberately so creation order and modification order DISAGREE:

  id6 "D and D session four: the party met a lich in the crypt."  <- created LAST
  id5 "the cat" + triangle                                        <- created before it

Then two more strokes were drawn on id5 (the older page).

$ ns_eval, walking the timeStamp cursor:
"now=64477418 id6 ts=64477415 mod=64477415 n=1 |
              id5 ts=64477411 mod=64477418 n=6 |
              id4 ts=64477407 mod=64477408 n=3 | ..."

id6 is newest by timeStamp. id5 is newest by EntryModTime. A7 answered from
id6. A9's FindNewest scan picked **id5**:

  INK PROMPT '... The drawing is accompanied by this note text: the cat'
  10.42.0.1 - - "POST /ink HTTP/1.0" 200 -

Transcript (a9ask-11-modorder-reply.png):
  Note: the cat
  Ink: A cat.

Render a9ask-12-modorder-render.png shows the triangle **plus the two crossing
strokes** as separate strokes — the property the deleted canvas never had.

TWO OPERATIONAL FACTS about EntryModTime, measured here, not previously
written down:

 (a) **It has one-minute granularity.** The first attempt drew on id5 in the
     same minute id6 was created, and both read mod=64477415 — a tie. The scan
     compares with strict `>` starting from the last entry, so on a tie the
     later-*created* note still wins. Two notes touched inside the same minute
     are therefore indistinguishable by modification.
 (b) **It is stale while the note is still on screen.** After the drag,
     Length(data) had already gone 5 -> 6, but EntryModTime still read the old
     value; it settled to 64477418 only after scrolling the Notepad away from
     that page. Leaving the note (switching to the chat app, as the real flow
     does) is what commits it.
